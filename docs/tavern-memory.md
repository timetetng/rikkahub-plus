# 长上下文一致性设计 · v2

> 目标：多楼层之后模型还能守住角色卡设定、记得前文事实、不漂移。
> 前置依赖：`PromptAssembler`（v1）。没有骨架/插槽这套语汇，"摘要放哪"根本没法干净地回答。

---

## 1. 先纠正一个直觉

「上下文有限 → 所以要压缩」只对了一半。

真正让角色崩掉的**往往不是容量，是距离**：

| 失败模式 | 真因 | 压缩能治吗 |
|---|---|---|
| 角色卡设定漂移 | 设定在 prompt 最开头，离生成点几百条消息远 | ❌ 压了还在开头 |
| 行为约束失效（别替用户说话…） | 同上，被长历史稀释 | ❌ |
| 忘记前文事实 | 要么被砍了，要么淹没在中段（lost in the middle） | ⚠️ 只治被砍的 |
| 状态错乱（谁在场、在哪、关系） | 没有权威记录，模型每次从历史重推，重推就错 | ❌ |
| 上下文溢出 | 物理上没了 | ✅ |

所以设计是**两条腿**：

- **近处钉住** —— 治注意力漂移，靠位置，不依赖召回
- **远处归档** —— 治容量，靠压缩与召回

只做压缩（= 只做第二条腿），角色该漂还是漂。

---

## 2. 架构：两个锚点 + 两个归档

```
        ┌── 锚点（每轮都在，钉在生成点附近，不依赖召回）──┐
        │  ① Author's Note @ depth      （已有，位置调好即可）│
        │  ② 状态快照 State Snapshot    （★ 新增，核心）      │
        └──────────────────────────────────────────────┘
        ┌── 归档（治容量，按预算触发）──────────────────┐
        │  ③ 滚动摘要 Rolling Summary   （结构化，非自由文本）│
        │  ④ 长期记忆召回               （现有记忆改成按相关度取）│
        └──────────────────────────────────────────────┘
        （另有：世界书 constant 条目钉设定 —— 已有）
```

### ★ 关键区分：摘要「替代」，快照「追加」

这条决定了实现顺序，必须先说清：

| | 是否改变 depth 坐标系 | 能否在装配后插入 |
|---|---|---|
| **滚动摘要** | **会**——它吃掉最老的历史，后面所有条目的 depth 全变 | 必须**装配之后**做 |
| **状态快照** | **不会**——纯追加，不替换任何东西 | 装配后自由插入 |
| **记忆召回** | 不会——纯追加 | 装配后自由插入 |
| **AN** | 不会——已有机制 | 已有 |

所以：

```
完整历史 → 算 depth / 激活世界书 / 按预设装配 → 得到 tagged 序列
                                              ↓
                                   ① 老历史换成摘要（改坐标）
                                   ② 在指定 depth 追加 召回 + 快照 + AN
```

顺序反了，世界书的 sticky/cooldown 与正则的 `minDepth/maxDepth` 全会错位。

## 3. 装配后的最终序列形态

```
[ main ]
[ charDescription ] [ charPersonality ] [ scenario ]
[ worldbook before/after char ]
[ dialogueExamples ]
[ chatHistory ]
    ├─ 【摘要】老历史压成的一条                     ← 位置：chatHistory 头部
    ├─ …未被压缩的历史…
    ├─ 【记忆召回】相关事实 top-k                    ← depth ≈ 8
    ├─ 【状态快照】当前状态块                        ← depth ≈ 4   ★
    ├─ 【Author's Note】                            ← depth ≈ 4（已有，默认值）
    └─ …最后几条最新消息…
```

depth 全部可配。默认值参考酒馆习惯（AN 默认 depth 4）。

## 4. 状态快照（核心）

### 为什么它比 MVU 更该内建

用户不要 MVU，是对的——MVU 的价值**不在那支 JS**，在它发明的模式：**每轮把当前状态重写一遍、钉在生成点附近**。
那个模式可以在原生实现，且能做得更好（可手改、可回退、不依赖卡里代码）。

### 数据结构

对话级持久化（不是助手级），结构而非自由文本：

```kotlin
@Serializable
data class ConversationState(
    val conversationId: Uuid,
    val version: Int = 0,              // 每次重算 +1
    val updatedAt: Long = 0,
    val scene: String = "",            // 地点 / 时间
    val present: List<String> = emptyList(),   // 在场角色
    val relationship: List<StateFact> = emptyList(),  // 关系变化
    val inventory: List<String> = emptyList(),        // 关键物品
    val threads: List<StateFact> = emptyList(),       // 未收尾的线
    val notes: String = "",            // 自由补充
    val source: StateSource = MANUAL,  // MANUAL / AUTO / IMPORTED
)

@Serializable
data class StateFact(val key: String = "", val value: String = "")
```

### 生成方式

- **增量**：输入 = 上一版快照 + 最近 N 轮（默认 12），输出新快照。**不重读全文**——否则成本随对话长度线性涨
- **失败回退**：解析失败 / 调用失败 → **沿用上一版**，绝不空窗、绝不把空状态注入
- **可手改**：界面上直接编辑。这比 MVU 的黑盒强，出问题能立刻纠正
- **首版引导**：没有快照时，从角色卡 + 前几条消息生成一次

### 渲染

进 prompt 时渲染成一段紧凑文本，例如：

```
<state>
地点：旧书店二楼
在场：沈墨、行简
关系：行简已开始把沈墨当搭子（信任 ↑）
物品：墨绿信封、备用钥匙
未收尾：与三叔的对峙尚未结算
</state>
```

用 `<state>` 包起来，方便正则/宏识别，也方便调试视图高亮。

## 5. 滚动摘要

### 触发
装配后总 token（历史 + 预设 + 世界书 + 快照）> `contextSize × 阈值`，默认 **0.75**。
不按轮数——压缩能设无限制时，阈值是唯一闸门。

### 形式：结构化，不要自由文本

自由文本摘要最容易丢设定。固定三段：

```
【已发生】…
【关系变化】…
【未收尾】…
```

### 增量合并
输入 = 上一版摘要 + 被压掉的那段（几十条），输出新摘要。
**不是每次重读全文**。

### 压多少
压到装配后总量回落到 `contextSize × 0.5` 左右，一次压够，避免每轮都触发。

### 硬约束
**必须装配之后做**（见 §2）。

## 6. 记忆召回

现状是「工具注入」——模型得自己想起来去查。改成**装配时按相关度召回**：

- 打分用**本地关键词 / BM25 式**，零依赖、零模型
- 候选就是现有 `AssistantMemory`（几十到几百条），关键词够用
- 用最后一条用户消息做查询，取 top-k（默认 4），低于阈值的不要
- **刻意不上 embedding**：Android 上引向量模型太重，且记忆条目规模根本不需要。这是取舍，不是遗漏
- 召回的条目钉在 depth ≈ 8，和摘要区分开

---

## 7. 执行时序：维护在后台，不在关键路径

快照重算和摘要生成都要调模型，**绝不能阻塞主生成**。

```
第 N 轮生成结束
   ↓
（异步，不阻塞 UI）判断是否该维护
   ├─ 轮数到点 → 重算快照
   └─ token 过阈值 → 生成本轮摘要
   ↓
结果写库；下一轮装配时自然生效
```

失败、超时、被系统杀掉 → 上一版继续用，用户无感。

---

## 8. 模型配置

需要一个**辅助模型**（可以是主模型，也可以单独配便宜的）：

- 摘要与快照重算共用
- 配置项：`memoryModelId`（null = 用当前对话模型）
- 温度建议低（0.2~0.3），这是结构化任务不是创作

---

## 9. 开关与验收

**默认全部关闭。** 理由：

1. 它们都是「额外注入」，会让消息序列和酒馆不一致
2. 用户开了才生效 → v1 的验收基线（逐条一致）不被破坏

开了之后，验收降级为：「**剔除注入块（摘要/快照/召回）后逐条一致**」。

必须提供调试视图：这一轮压了哪几条、摘要是什么、快照是什么、召回了什么。不然出问题没法定位。
